# Image handling

Recipe uploads are handled in two stages:

1. The iOS client prepares selected photos before creating the multipart
   request. It corrects orientation, scales very large photos down, removes
   picker metadata, and targets an upload size below the backend's 25 MB
   original-file limit.
2. The API retains the uploaded file while the recipe is private and queues
   predictable `thumbnail` (480 px) and `detail` (1600 px) WebP derivatives.

The backend's metadata policy is deliberate:

- Private originals are retained for the owner while the recipe is private.
- Publishing never exposes the original file. The unqualified image URL for a
  published recipe resolves to the sanitized `detail` derivative.
- `thumbnail` and `detail` derivatives are re-encoded as WebP with EXIF/GPS
  metadata stripped. The original variant is rejected after publication.
- Every image variant is still authorized by the recipe image policy before
  storage access. Published derivatives are cacheable; private responses are
  private and short-lived.

The API enforces a maximum of five images per recipe, a 25 MB maximum original
file size, and a 5 GB per-user quota. Validation errors are returned through
the normal API error envelope so the iOS client can distinguish quota errors
from transport failures and offer a retry.

Image derivatives are generated by the queue worker. While processing, the
resource reports `processing_status: pending`; it reports `ready` after both
configured derivatives are stored, or `failed` when processing cannot finish.
