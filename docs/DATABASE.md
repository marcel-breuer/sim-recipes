# Database design

The Laravel API uses PostgreSQL for the durable SimRecipes domain model. All
externally exposed domain identifiers are ULIDs, generated by Eloquent's
HasUlids trait. Foreign keys are explicit and indexed; relationship tables
use composite primary keys to prevent duplicate associations.

## Core tables

- users and profiles store the minimum account identity and public profile
  data. Apple subject identifiers are unique when present.
- camera_models and camera_capabilities describe supported cameras and the
  settings they expose. Recipe settings reference capabilities instead of
  embedding camera assumptions in application code.
- recipes stores metadata, target camera, lifecycle state, and popularity
  counters. private recipes have no published_at; published recipes must
  have one. The database constraint protects this state shape, while the
  publication service will enforce immutability.
- recipe_settings and recipe_images store structured settings and image
  metadata. Original image paths are retained separately from asynchronous
  derivative metadata. Image size and five-position ordering limits are also
  constrained at the database boundary.
- categories, tags, category_recipe, and recipe_tag represent the predefined
  multi-select categories and separate free-form tags.
- recipe_provenances records the source recipe, source author when available,
  and account that created a copy. A copy is a normal private recipe in the
  same recipes table.
- likes, recipe_views, and recipe_downloads are separate event/relationship
  tables. Their data supports independently replaceable popularity calculations;
  counters on recipes are maintained by later application services.

The one-image minimum, five-image maximum, per-user 5 GB quota, and private
image authorization require request/service and storage checks because they
cannot be enforced safely by a row-level database constraint alone.

## Migration verification

The backend test suite runs against PostgreSQL. A fresh database migration is
required before schema tests, and the backend CI job provisions an isolated
PostgreSQL service for that purpose.
